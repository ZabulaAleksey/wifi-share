# WiFi Share — локальные инструкции

Перед началом работы прочитай `~/.codex/AGENTS.md`.

## Контекст проекта

- Обмен файлами в локальной сети с backend на Go и frontend на React/Vite в каталоге `web/`.
- Текущий этап, статус, blockers, evidence и NEXT принадлежат только `docs/STAGES.md`; `docs/ROADMAP.md` задаёт порядок будущих фаз.
- На каждой границе файловой системы или сети сохраняй проверку нахождения пути в разрешённой области, аутентификацию, безопасную обработку медиафайлов и допущения о работе только в LAN.
- `config.local.json`, общие данные, пароли и локальные пути должны оставаться неотслеживаемыми; обновляй `config.example.json` только безопасными заполнителями.
- Не редактируй вручную сгенерированные исполняемые файлы или результат сборки frontend.

## Проверки

- Backend: `go test ./...`
- Frontend: из каталога `web/` выполни `pnpm lint` и `pnpm build`
- Канонический frontend package manager — `pnpm@11.23.0` с `web/pnpm-lock.yaml`; restore выполняется через `pnpm install --frozen-lockfile`. Общий store разрешён, `web/node_modules` disposable. При блокировке `pnpm.ps1` используй `pnpm.cmd`.

Читай только относящиеся к задаче документы по архитектуре и безопасности и правила AI Dev Team; не загружай заранее все правила, файлы SPEC или `LEARNING_LOG.md`.


## Локальные правила тестирования

### Тестовый контракт
- После принятия тестов/fixtures/golden-сценариев они считаются контрактом и не изменяются в том же цикле генерации.

### Unit / integration / component
- Backend: `go test ./...`
- Frontend component/sanity: `cd web; pnpm lint` и `cd web; pnpm build`
- Интеграция API+frontend: запускать backend и frontend-проверки в одной итерации перед релизом.

### E2E (критические)
1. Инициализация и обнаружение peer-узла.
2. Создание и отображение стрим-сессии между двумя сторонами.
3. Корректное завершение сессии при разрыве соединения.

- Если стенд с несколькими устройствами/бо́льшей сетью недоступен: `BLOCKED_BY_BACKEND_WIFI_SHARE`.
